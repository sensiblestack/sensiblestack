Your Make credits are disappearing, and nothing is broken

If the balance is falling, the account is not leaking. Make charges for operations that actually execute. Idle polling checks that find nothing cost nothing in our test. The drain is a scenario whose action steps fire on every run.

What the test showed

On 23 November 2026 we ran a credit burn demo in our own Make account. The scenario ran 227 times in about 56 hours. It used 16 of 1,000 credits in total. 221 runs cost 0, because the watch trigger found nothing new and the action step never ran.

An earlier version of this page treated every wake-up as a charge, including the ones that found nothing. That reading did not survive the test. Make charges for operations that actually execute. An idle check that finds nothing, and never starts the action step, cost nothing here.

Where the credits actually go

Most scenarios start with a trigger whose name begins with Watch. On a schedule, the scenario asks the other app whether anything new has arrived. In the test, when that watch found nothing new and the action step never ran, the run cost 0.

The real drain is a scenario whose action steps fire on every run. A trigger that returns data each time starts the modules after it on every wake-up. An iterator over many items repeats those modules, once per item. A module that runs regardless executes on every run, whether or not the watch found something new. That is the design to look for when the balance moves and the useful work looks small.

The fix, in the order to try it

1. Find the drain before you fix anything. In Make, open your organisation's usage view and the Scenarios list, and see which scenarios are consuming the credits. Then open a hungry scenario's history. The runs that cost money are the ones where modules after the trigger actually executed. An empty watch was not the spend in our test.

2. Use an instant webhook where the app offers one. An instant trigger runs the scenario when something happens, through a webhook, rather than on a clock, so the action steps do not fire on a schedule. Look for the same app's trigger marked INSTANT. Where an app has no instant trigger, a webhook or mailhook module can do the same job for form and email sources.

3. Match the schedule to the job. In the scenario's Schedule settings, pick the slowest interval the work tolerates. A 15 minute watch that finds nothing was not, by itself, a credit leak in our test. It becomes one when the action steps fire on every run: a tighter interval then means more executions. Hourly, or twice a day, is enough for plenty of jobs.

4. If several scenarios do the same work, merge the actions. One trigger, then a Router splitting the flow, means the shared steps run once instead of once per scenario. Routers cost no credits. Merging does not save money on empty checks. It saves it when the action steps were going to run in each scenario.

5. Trim what happens after the trigger. Put filters immediately after the trigger so unwanted items stop before later modules run. Filters, routers and error handlers cost no credits themselves. Drop modules a run does not need, because a module that executes is what the meter charges for. Where a scenario walks many items one at a time before a single action, an aggregator can combine them into one bundle first, so that action runs once.

The honest limits

Some apps offer no instant trigger, and polling on a sensible interval is a normal way to watch them. Idle checks that find nothing cost nothing in our test, so the schedule is not the mistake. The mistake is a scenario whose action steps fire on every run: a trigger that returns data each time, an iterator over many items, or modules that run regardless. Filter early, drop modules you do not need, and set a schedule the job actually requires.
